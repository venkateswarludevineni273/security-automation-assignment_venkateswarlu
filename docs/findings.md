# Security Findings

VulnTracker stores a security team's list of unfixed weaknesses in their own systems. That makes it a high-value target: an attacker who reads it gets a ready-made list of where to attack its owner. I rated severity with that in mind, not by CVSS score alone.

**Severity scale (applied to this application):**
- **Critical** - an unauthenticated or trivially exploitable path to read or change every customer's data, or to impersonate any user.
- **High** - exposes one customer's or user's sensitive data to another, or leaks credentials; needs a login or a precondition.
- **Medium** - weakens a control or helps an attacker once they have a foothold; limited direct impact.
- **Low** - hardening gaps and nuisance-level issues.

**Status column:** reflects the final state of `main`. Rows marked *Fixed* were fixed in two passes (first the critical and high findings, then everything that could be fixed in code or CI); what is still open is listed in `remediation-plan.md`.

**Where "Where" says:** *starter* = code that came with the assignment; *new feature* = the Shared Report Link code I wrote in Task 1.

## 2. Findings in the starter code - Python API (`app/`)

| ID | Finding | Detected by | Severity and why | Business impact in VulnTracker | Where | Status |
|----|---------|-------------|------------------|--------------------------------|-------|--------|
| F1 | **Login tokens accept the "none" algorithm** (`auth.py`: `algorithms=[ALGORITHM, "none"]`). Anyone can write an unsigned token naming any username and the API accepts it. | Manual. Bandit does not flag it. | **Critical.** No credentials, no skill, one line of work. Defeats authentication completely. | An outsider can act as any user, read every customer's findings, change statuses, delete records, and create share links to exfiltrate reports. | starter | **Fixed** (algorithm pinned; `exp` and `sub` required; regression test) |
| F2 | **Secrets committed to source**: JWT signing key, database password, admin API key (`config.py`), and the notify service key (`notify/src/config.js`). | Bandit B105 flagged 2 of the 4 (those named "password"/"key=" strings). Missed the admin API key and the notify key. | **Critical.** The repo is public, so the signing key lets anyone mint valid tokens *even after F1 is fixed*. | Total loss of authentication. Removing the lines does not help: they are in git history and must be treated as burned. | starter | **Partly fixed.** App: moved to environment/mounted file, app refuses to start without a key. The notify key is also gone from source (N1). **Not fixed, and cannot be fixed in code:** all four old values remain in git history, so they must be **rotated** (remediation plan R1). |
| F3 | **SQL injection in `/scans/search`**: the search text is pasted into a raw SQL string. | Bandit B608 (rated Medium); **I raised it to High** after proving a `UNION` can read the `users` table. | **High.** Needs a login (so not Critical) but exposes password hashes and every user's scans. | Account password hashes and other customers' vulnerability data can be read, possibly modified depending on the database driver. | starter | **Fixed** (bound parameters, `LIKE` wildcards escaped; regression tests) |
| F4 | **Broken access control (IDOR)**: `GET /scans/{id}` and `/scans/search` return any user's scans, unlike update/delete which check the owner. | Manual. | **High.** Any registered user can read every other user's findings by counting up ids. | A customer sees a competitor's unpatched weaknesses. The most damaging data in the product. | starter | **Fixed** (owner enforced; non-owner gets the same 404 as "missing") |
| F5 | **Plaintext passwords written to logs** on every login attempt, successful or not (`main.py`). | Manual. | **High.** Logs are widely readable and long-lived, and people mistype passwords from other accounts. | Anyone with log access (support, a log-vendor breach) harvests working credentials. | starter | **Fixed** (password no longer logged; regression test) |
| F6 | **Vulnerable dependencies** - 67 advisories in `fastapi`, `starlette`, `python-multipart`, `python-jose`, `cryptography`, `anyio`, `pytest`, `ecdsa`. | pip-audit. | **High overall, but triaged individually.** `python-jose` (6, including algorithm confusion) sits on the login path, so **High**. `python-multipart` and most `starlette`/`cryptography` advisories are in form/upload/TLS code this API never calls, so **Low** in practice. `ecdsa` has no fix. | Without triage this looks like 67 emergencies. In reality one library on the auth path mattered; the rest was unused code. | starter | **Fixed**: swapped `python-jose` for PyJWT, removed the three packages the app does not use, upgraded the rest. pip-audit is now **0 vulnerabilities** (`reports/post-remediation/`). |
| F7 | **CORS reflects any origin with credentials allowed** (`main.py` middleware). | Manual. | **Medium.** Authentication uses a header token, not cookies, so a hostile site cannot ride a browser session today. It becomes High the day cookies are added. | Defeats the browser's main protection between sites. | starter | **Fixed** (opt-in allowlist via `CORS_ALLOWED_ORIGINS`, credentials off) |
| F8 | **Stack traces and exception text returned to clients** (global handler). | Manual. | **Medium.** No direct breach, but it hands attackers file paths, library versions and query text. | Makes every other attack easier (it is what you would use to tune F3). | starter | **Fixed** (generic 500; detail goes to the server log only) |
| F9 | **No brute-force protection on login**, no password policy (`"pw"` is accepted), and registration reveals whether a username/email exists. | Manual. | **Medium.** Combined with F5-style credential reuse this is how real accounts get taken over. | Account takeover by guessing; user enumeration. | starter | **Partly fixed.** Password minimum of 10 characters; one generic message when a username or email is taken; ingress rate limit (10 requests/s, 20 connections) in the Helm chart. **Not built:** per-account lockout or throttling inside the app (needs shared state; see R2). |
| F10 | **Disabled users still work**: `is_active` is stored but never checked at login or on requests. | Manual. | **Medium.** Offboarded staff keep access until their token expires, then can log in again. | Ex-employees retain access to customer vulnerability data. | starter | **Fixed.** Checked at login and on every request, so a disabled account stops working immediately; tests for both. |
| F11 | **Unbounded `limit` on `GET /scans`** and no length limits on text fields. | Manual. | **Low.** Easy to abuse for resource exhaustion, but needs a login. | Slow or unavailable service for one user's very large request. | starter | **Fixed.** `limit` capped at 1-100, `skip` at 0 or more, text fields length-limited; tests. |
| F12 | **Local SQLite database, no encryption at rest, no backups.** | Manual. | **Medium** for a production service. | Data loss on a node failure; data readable from a stolen disk. Also forces single-replica deployment. | starter | **Deferred** (R5) |

## 3. Findings in the Node.js notification service (`notify/`)

The brief says this service needs no changes, so my first pass only assessed it and documented the risk. In a second pass I hardened it anyway, because a service that can be made to call internal addresses and hand out its own key should not be left that way; the changes are small, covered by tests, and the existing behaviour is unchanged for authorised callers.

| ID | Finding | Detected by | Severity and why | Business impact | Where | Status |
|----|---------|-------------|------------------|-----------------|-------|--------|
| N1 | **No authentication on `/webhooks` and `/notify`**, anyone who can reach the port can register a webhook; the service then POSTs to **any URL** (server-side request forgery) and **attaches its secret `X-Service-Key` header** (hardcoded in source). | Manual. | **High** while it is internal-only (as designed and as the Helm chart enforces); **Critical** if ever exposed. | An attacker registers a webhook pointing at the cloud metadata address or an internal admin service, and the server calls it for them; or points it at their own server and collects the service key. | starter | **Fixed in code.** Bearer token required on every route except `/health` (fails closed); webhook URLs must be https, no credentials, no private, loopback, link-local or metadata addresses, checked again at connect time; payloads are HMAC-signed and the shared key is no longer sent to receivers or stored in source; redirects off. 21 tests. |
| N2 | **Vulnerable npm dependencies**: 11 advisories, including **1 critical** (`proxy-addr`) and 5 high (`axios`, `express`, `body-parser`, `path-to-regexp`, `follow-redirects`). | npm audit. | **High.** Most are denial-of-service or redirect issues in a service that is not internet-facing; the critical (IP spoofing) only matters if the app trusts proxy headers, which it does not. Rated by reachability rather than by the tool's label. | Service outage or request-forgery weaknesses if the service is later exposed. | starter | **Fixed.** axios 1.21.0, express 4.22.3, `uuid` replaced by Node's `crypto.randomUUID`. npm audit: **11 to 0** (`reports/post-remediation/sca.npm-audit.json`); CI now fails on high or critical. |
| N3 | **Error handler returns stack traces.** | Manual. | **Medium.** | Information leak. | starter | **Fixed.** Generic 500; malformed JSON gives a plain 400; delivery errors no longer expose internal addresses. |
| N4 | **Python API to notify service is plain HTTP, unauthenticated.** | Manual. | **Medium.** Scan titles and owner names travel in clear text inside the cluster. | Any workload that can reach the pod can read or inject events. | starter | **Partly mitigated.** Calls are now authenticated with a bearer token (from the secrets manager in the chart), and the API's NetworkPolicy limits who can reach it. Traffic is still unencrypted inside the cluster, and the notify pod needs its own NetworkPolicy when it is deployed (R6). |

## 4. Findings in the new feature (Shared Report Link)

I reviewed my own Task 1 code the way I would review someone else's, and found two real issues.

| ID | Finding | Detected by | Severity and why | Business impact | Where | Status |
|----|---------|-------------|------------------|-----------------|-------|--------|
| S1 | **Password-guess limit could be raced.** The 5-attempt lock read the counter, then wrote it back; several simultaneous requests could all see "0 failures" and each get a guess. | Manual review of my own code. | **Medium.** Needs the link *and* parallel traffic; turns "5 guesses" into "as many as the server can handle". | Weakens the password on a shared link. | new feature | **Fixed.** Attempt is reserved with one atomic database update before the password is checked; test proves the counter never exceeds 5. |
| S2 | **Password sent in the URL query string** (`?password=`), as the brief specifies. Query strings are recorded in access logs, proxies and browser history. | Manual. | **Low.** Exposure is to people with log access. | A link password can end up in logs. | new feature | **Mitigated.** `X-Share-Password` header is now accepted and preferred; query string kept for brief compatibility. The access log now redacts `/share/<token>` and `?password=`; proxy or ingress logs outside this service may still record them (R8). |
| S3 | **Lockout can be triggered by anyone holding the link**, and there is no way to unlock or revoke a link. Wasting the 5 attempts locks the legitimate viewer out until the owner creates a new link. | Manual. | **Low.** Requires the unguessable link already. | A disgruntled forwardee can block an auditor's access. | new feature | **Mitigated.** The owner can list a link's state (including `locked`), revoke it, and issue a new one. A link-holder can still burn the 5 attempts, so the lock remains a nuisance, not a breach (R8). |
| S4 | **Shared page shows the *live* scan, not a snapshot**, so later edits to remediation notes become visible to the external viewer for the whole 24 hours. | Manual. | **Low.** Design choice, but surprising. | Internal notes added after sharing could leak. | new feature | **Fixed.** The public view is a snapshot taken when the link is created; later edits never reach the viewer. Test proves it. |
| S5 | Expired links stay in the database; no way to list or revoke links. | Manual. | **Low.** | Clutter; no emergency "kill this link" button. | new feature | **Fixed.** `GET /scans/{id}/shares`, `DELETE /shares/{id}` (owner only), expired links purged on the next share, and audit log lines for create, access, failure, lock and revoke that never contain a token or password. |

**Things the feature already does well** (and I would point to in review): 256-bit random token stored only as a SHA-256 hash; password stored with bcrypt; owner-only creation with the same 404 for "not yours" and "does not exist"; identical 404 for unknown and expired tokens; public response omits internal ids; `Cache-Control: no-store`; links die with their scan; `share_url` built from configuration, not from the client-supplied `Host` header.

**What I deliberately did well in the deployment** (worth pointing at in an interview): non-root numeric UID, read-only root filesystem, all Linux capabilities dropped, no privilege escalation, resource requests and limits, ingress NetworkPolicy limited to the ingress controller, and the signing key synced from a secrets manager by External Secrets and mounted as a file (`SECRET_KEY_FILE`), not set as an environment variable or written in the manifests.

**What I could not verify locally:** this workspace has no Docker daemon and cannot reach image registries, so I did not build or run the image myself. The build, "runs as non-root", "refuses to start without a secret" and "healthy and reachable" checks run in CI (job `container-scan`), and that job passed.
